# Design intent, behavior and architecture

> **Status:** Maintained reusable procedure · Target-project rules retain authority


- Read current owner conclusions and reversal history first, then product/design authority, actual types/architecture, component system, platform rules and relevant proposal. Historical rebuild prompts do not override current contracts.
- Separate locked product decisions, implementation gaps and unresolved design choices. An unbuilt decided feature is not permission to reopen its design. Record a genuine owner revision without erasing prior history.
- Define actor, job, journey, current pain, intended behavior, success/failure, non-goals and acceptance. Explore bounded alternatives only when a meaningful choice remains.
- Specify information hierarchy, controls, data ownership, states, focus/keyboard behavior, labels, errors, loading/empty states, responsive layout and accessible semantics for UI work.
- Reuse each project's components/tokens and extension rules. Do not impose a web component stack on native, Python or game projects. Shared design-system pointers own their respective conventions.
- Architecture work names responsibility boundaries, interfaces/types, data flow, trust boundaries, dependency order and recovery. For games, keep gameplay rules, content assembly and display ownership aligned with the project's architecture.
- Creative/content work follows its source/rights/voice and publication rules. Preview, draft, owner audition, shipped feature and published output are separate states.
- Express buildable contracts and realistic seeded examples, not only aspirational prose. Name behavior of existing data/projects when defaults or templates change.
- Inspect actual visual/rendered output where design acceptance requires it. Implementation cannot approve subjective owner choices on the owner's behalf.
- Record a simple conclusion and generate the design/proposal/build prompt with source references, constraints and concrete acceptance. Use templates/DESIGN.md.
